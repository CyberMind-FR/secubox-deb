# Anti-Track v2 — Plan 2b-DNS: pure-tracker DNS-refuse via unbound

- **Date:** 2026-06-17
- **Package:** `secubox-toolbox`
- **Issue:** #633
- **Status:** Design approved (resolver topology live-verified), pending implementation plan
- **Parent:** Plan 2b enforcement design (§5, which assumed dns-guard — CORRECTED here)
- **Builds on:** Plan 2a (`pure-trackers.txt`) and Plan 1 (`privacy_enforce`/`privacy_dns_feed` toggles).

---

## 1. Goal

Add the cheapest hard-block layer: make confirmed **pure-tracker** domains return
**NXDOMAIN** to the inspected clients, so trackers never resolve — covering even
flows that bypass the proxy. Driven by `pure-trackers.txt` (consistent with the
block-vs-poison split: only pure trackers are hard-blocked; load-bearing are
poisoned at HTTP).

## 2. Resolver topology (LIVE-VERIFIED on gk2, 2026-06-17)

`ssh root@10.98.0.1` probe confirmed:
- **unbound is the active resolver** for inspected clients — listens on
  `10.99.0.1:53` + `10.99.1.1:53` (WG R2/R3 peers) and `10.100.0.1:53` (LXC).
- **`secubox-dns-guard` is INACTIVE**; dnsmasq listens only on `10.0.3.1:53`
  (libvirt/LXC NAT bridge — not the client path).
- unbound has `remote-control.conf` + `/usr/sbin/unbound-control` present;
  existing drop-ins `98-secubox-lxc.conf`, `99-secubox-wg.conf` in
  `/etc/unbound/unbound.conf.d/`.

**Conclusion:** the DNS-refuse feed must target **unbound**, not dns-guard. The
parent spec's "feed dns-guard blocklist.txt" was wrong for this board — corrected.

### Decisions

| Question | Decision |
|---|---|
| Resolver | **unbound** (live-verified the client resolver; dns-guard inactive) |
| Mechanism | toolbox-owned unbound drop-in + `unbound-control reload` |
| Refuse verb | `local-zone: "<domain>." always_nxdomain` |
| Source list | `pure-trackers.txt` (hard-block list), NOT all learned trackers |
| Gating | `privacy_enforce && privacy_dns_feed` (dark by default) |

## 3. Architecture

```
sbin/secubox-toolbox-autolearn   (hourly — EXTENDED, after pure-trackers.txt write)
   if privacy_enforce and privacy_dns_feed:
       ip_dns.write_unbound_block(pure_hosts, conf_path)   → atomic write drop-in
       reload unbound (unbound-control reload || systemctl reload unbound)

secubox_toolbox/ip_dns.py        (EXTENDED — Plan 2b module)
   • unbound_block_lines(pure_hosts) -> list[str]
        → ['local-zone: "criteo.com." always_nxdomain', ...] (sorted, deduped, registrable)

/etc/unbound/unbound.conf.d/97-secubox-antitrack-block.conf   (NEW, generated)
   server:
       local-zone: "criteo.com." always_nxdomain
       local-zone: "doubleclick.net." always_nxdomain
       ...
```

**Files**
- **Extended:** `secubox_toolbox/ip_dns.py` (`unbound_block_lines`, pure formatter),
  `sbin/secubox-toolbox-autolearn` (gated write + reload step),
  `tests/test_ip_dns.py` (new test), `debian/changelog`.
- **Generated at runtime:** `/etc/unbound/unbound.conf.d/97-secubox-antitrack-block.conf`.
- **Reused:** Plan 1 toggles + master gate; Plan 2a `pure-trackers.txt`; the existing
  unbound drop-in directory + `unbound-control`.

**Boundary.** `unbound_block_lines` is pure (hosts → config lines, no I/O). The
autolearn step does the atomic file write + reload. Same pure/imperative split as
the rest of the anti-track code.

---

## 4. The unbound drop-in

- Path: `/etc/unbound/unbound.conf.d/97-secubox-antitrack-block.conf` (sorts AFTER
  the existing `98`/`99` — wait: 97 sorts BEFORE 98/99; that is fine, `local-zone`
  directives are additive and order-independent within unbound's config). The `97`
  prefix is chosen so it loads alongside the secubox drop-ins; an env override
  `SECUBOX_UNBOUND_BLOCK_CONF` lets tests target a temp path.
- Content: a single `server:` clause with one `local-zone: "<reg>." always_nxdomain`
  per pure-tracker registrable domain. `always_nxdomain` makes the zone and all
  subdomains return NXDOMAIN — so `www.criteo.com` and `criteo.com` both refuse.
- Generated by `unbound_block_lines(pure_hosts)`: registrable-fold (reuse
  `privacy.registrable`), dedupe, sort, emit the `local-zone` lines under a
  `server:` header + a generated-file banner comment.

## 5. autolearn step (gated, fail-safe)

After the `pure-trackers.txt` write, gated by `privacy_enforce && privacy_dns_feed`
(read from `filters.get_filters()`):
1. Build the drop-in text via `ip_dns.unbound_block_lines(pure_hosts)`.
2. Atomic write (temp + `os.replace`) to the drop-in path.
3. Reload: `unbound-control reload` (fallback `systemctl reload unbound`),
   `subprocess` with a short timeout; failure is logged, **non-fatal**.

**Fail-safe:**
- `_learn`/filters unavailable, or gate off → do not touch the drop-in (leave
  last-good in place). Mirrors the pure-trackers.txt degraded-mode rule.
- Empty/missing pure list → write an empty `server:` drop-in (no `local-zone`
  lines) → no refusals (fail toward fewer blocks). Reload still applied so a
  previously-populated drop-in is correctly cleared when the list empties.
- Any write/reload exception logged, autolearn run continues.

## 6. Config / error handling / tests

- **Config:** reuse Plan 1 toggles; no new keys. `privacy_dns_feed` default True but
  double-gated behind `privacy_enforce` (False) → dark.
- **Tests (`tests/test_ip_dns.py`):**
  - `unbound_block_lines(["www.criteo.com","doubleclick.net","criteo.com"])` →
    a `server:` header + exactly two `local-zone: "criteo.com." always_nxdomain`
    / `"doubleclick.net." always_nxdomain` lines (registrable-folded + deduped +
    sorted); empty input → just the `server:` header (no local-zone lines).
  - autolearn integration (extend the existing subprocess test or add one): with
    `privacy_enforce=true && privacy_dns_feed=true` and a seeded pure list, the
    drop-in file is written containing the expected `local-zone` line; with the
    gate off, the drop-in is NOT written. (Reload is stubbed/skipped in tests via
    env — `SECUBOX_UNBOUND_RELOAD=0` no-ops the reload subprocess.)

## 7. Rollout / arming

Dark by default. Arm order (after 2b-IP soak): set `privacy_enforce=true` (this
also turns on poison + anonymize + the DNS feed of pure trackers). Before arming,
the operator confirms unbound is still the client resolver (it is, per the live
probe). `unbound-control reload` is fast and reversible (removing the drop-in +
reload restores resolution). Audit: the autolearn manifest line already reports
counts; extend it to note the DNS drop-in size.

## 8. Out of scope

- dns-guard integration (inactive on the board; wrong resolver).
- Per-client DNS policy (the drop-in is board-wide for all unbound clients —
  acceptable: pure trackers should be refused for everyone).
- `#filtres` / `#social` UI (Plans 2c / 2d).
